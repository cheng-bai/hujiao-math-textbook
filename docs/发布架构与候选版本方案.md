# 发布架构与候选版本方案

日期：2026-10-22。调查基线：`3b0541d`。

**状态：方案与下一轮实施合同，尚未接管发布。** 本轮只更新文档和 AI 任务路由；不生成候选网站、不改正文、不替换 Pages 工作流、不推送或部署。下文拟新增命令和目录均标为计划，不能当作现成工具执行。

## 1. 目标与非目标

目标是让任何接手 AI 都能回答：准备发布哪些文件、为何可发布、依据哪个提交检查、由谁确认、上线的是不是同一版本。

采用现有 Python + 原生网页 + GitHub Actions/Pages。借鉴个人网站的“来源与成品分离、可重复构建”，不引入 Astro、数据库、Docker 或 Dokploy。

本轮不处理正文润色、题目难度、图片重绘或运行代码大重构；也不把自动检查升级成数学/教学审定。

## 2. 当前事实与风险

### 当前发布路径仍然有效，尚未改变

`.github/workflows/pages.yml` 仅手动触发：

```text
checkout 工作流选中的版本
  -> 创建 _site
  -> 复制根 index.html、整个 outputs/、整个 batch/reviews/
  -> check_release.py --site-root _site
  -> 上传 Pages artifact -> 部署
```

当前 CI 与 Pages 是独立工作流。Pages 的 `workflow_dispatch` 本身不保证此前 CI 通过，也不代表内容审阅已完成；当前工作流没有候选摘要确认接口。

### 必须弥补的四个缺口

1. 复制整个 `outputs/` 会自动纳入以后被提交的新目录；Git 跟踪不等于获准公开。
2. 仓库检查与候选检查不是同一件事；检查当前目录后再从浮动 `main` 取文件，可能发布另一版本。
3. 推送、检查通过、获得确认、Pages 成功、线上一致是不同状态，不能合并成“发布完成”。
4. 当前 `--site-root` 只检查 HTML/CSS 引用存在，不足以证明白名单、敏感文件、动态载荷、学生包或数学正确。

### 本轮只读核对的依赖

根 `index.html` 指向五册入口。正式目录中 HTML/CSS 的跨根引用包括 `outputs/_shared/site-access.*` 和 `batch/reviews/`；正式教师页还依赖册级 `_sources/`。不能仅复制“正文 HTML”。

上述引用检查**没有证明 JavaScript 动态资源闭包、Markdown 链接、全部交互或线上功能均已验收**。下一轮组装器必须结合资源清单和实际浏览器检查，不能仅靠正则寻找链接。

## 3. 发布对象分成三类

| 类别 | 内容 | 是否进入公网网站 |
| --- | --- | --- |
| 编辑与构建输入 | `sources/`、节底稿、生成脚本、依赖配置 | 不因部署而整目录复制；仓库公开与网站部署是不同边界 |
| 阅读成品 | 允许的入口、正文、共享资源、图、学生 ZIP、必要公开说明 | 仅通过白名单和检查后进入候选 `site/` |
| 发布控制资料 | 精确文件清单、摘要、检查结果、确认记录、差异报告 | 放 `control/` 或 Actions artifact；默认不进入 `site/` |

教师网页本就包含答案，`private-*` 是区分用途的运行命名，不表示真实访问控制。不能全删 `private-*` 或 `_sources/` 来“修复学生隔离”，这会破坏教师版；学生隔离要检查学生 HTML、ZIP 与实验载荷自身。

公开 Git 仓库中的文件仍可被获取。发布白名单不是仓库保密、账号认证或教材内容授权机制。

## 4. 白名单采用“两道门”，不是只写一个 glob

### 第一门：版本化发布策略，规定哪些路径有资格

拟新增 `architecture/release-policy.json`，记录 schema、profile、允许根/精确文件、禁入规则、必要入口和策略变更说明。**该文件尚未创建，当前不被工作流读取。**

第一版使用 `public-current` 兼容档，保留已发布 URL，不在同一轮顺便下架旧演示。

| 路径 | v1 处理 | 原因与约束 |
| --- | --- | --- |
| `index.html` | 精确允许 | 网站入口，保留相对跳转 |
| `outputs/五册教材教参整合/` | 允许已审阅的跟踪文件集 | 五册页面、索引、ZIP、图、JSON、册级共享资源与来源快照；不凭扩展名删未知运行依赖 |
| `outputs/_shared/site-access.css`、`site-access.js` | 精确允许 | 册目录与总览实际引用，不能遗漏 |
| `outputs/教材可视化资源库/` | 兼容档显式允许，冻结包闭包 | 保持已公开资源 URL、manifest 和版本哈希；不原地重封存 |
| `outputs/教材可视化编排小样/` | 兼容档显式允许 | 旧演示 URL 独立保留；不因此宣称是正式教材功能 |
| `outputs/空间向量基本定理-最小试作/` | 兼容档显式允许 | 保留旧试作 URL，不提升教学认可状态 |
| `batch/reviews/` | 只允许逐文件审阅后冻结的公开子集 | 先保留当前链接需要的记录；不能默认把以后所有内部复核都发布 |
| 高清图/难度校准、本地新增目录 | 默认不允许 | 本地存在或 Git 跟踪都不代表已批准上线；单独加入策略并审阅 |

可在后续另设 `reader-core` 精简档，但须先列旧 URL 影响、运行依赖和重定向方案。它不是第一版默认，不为压缩体积静默删入口。

明确禁止：`.git/`、`.env*`（公开示例例外须精确批准）、缓存、依赖安装目录、私密学生资料、密钥、临时截图/PDF/日志、验证工作目录、`release-work/` 和未批准试点。禁入规则优先于目录级允许；symlink 和越界路径默认拒绝。静态扫描只能减少风险，不能保证发现所有秘密。

### 第二门：候选的精确文件集，规定本次实际发布什么

从固定 Git 提交的 tracked 文件构造，而不是递归复制本机工作区。第一轮先审阅白名单基线；以后与上次已确认 manifest 对比：

- 新路径，即使位于允许根内，也必须列为待确认新增项。
- 删除路径须显示被引用情况和 URL 影响；不是“文件少了就更安全”。
- 修改文件按摘要列明，关联章节/共享组件以及相应检查。
- dirty 工作区不混入候选。若修改尚未提交，只能预览 diff，不声称候选已经代表这些修改。

候选 manifest 对每个文件记录 `path`、`size_bytes`、`sha256`，路径按仓库相对 POSIX 格式排序；目录结构不扁平化、不重写中文 URL。检查 manifest 和候选树双向相等：缺文件、多文件、变字节都拒绝。

## 5. 候选目录与身份

拟使用被 Git 忽略的 `release-work/{release_id}/`，而不是塞进公开 `outputs/`。**当前尚无该目录、忽略规则或组装器。**

```text
release-work/{release_id}/
  site/                         # 唯一可上传的网页根
    index.html
    outputs/...
    batch/reviews/...            # 获准公开且必要的子集
  control/                      # 不进入网页根
    candidate.json              # 身份、策略、文件 manifest、质量状态
    changes.json                # 对上一确认版本的增删改
    checks.json                 # 本候选检查结果与证据摘要
  receipts/                     # 上传之后的外层回执，不写回冻结工件
    artifact.json               # 平台返回的工件身份，绑定 candidate_digest
    approval.json               # 明确确认后记录，不预生成批准
    deployment.json             # 部署与线上核对结果，不能改写冻结 checks
```

拟定身份字段：

| 字段 | 规则 |
| --- | --- |
| `release_id` | 人可读标识，不代替密码或内容身份 |
| `source_sha` | 完整 Git commit SHA，不用浮动分支名代替 |
| `policy_sha256` / `tool_digest` | 发布策略与组装/验证工具依据 |
| `files` / `site_digest` | 精确文件表；规范化排序序列计算摘要 |
| `checks_digest` | 检查报告及其工具、配置依据摘要；报告的 subject 是 `site_digest`，不反向引用 `candidate_digest` |
| `candidate_digest` | 对 `schema_version, profile, source_sha, policy_sha256, tool_digest, site_digest, checks_digest` 的规范化对象计算；不含自身、approval 或上传工件身份 |
| `artifact_id` / `artifact_digest` / `run_id` | 上传后保存到独立运输回执/平台元数据，绑定 `candidate_digest`；不能回写已上传的 `candidate.json` |

归档压缩可能带时间戳，不能用“不同时刻压缩包必须字节相同”替代文件树一致性。冻结后 `site/`、策略、工具或检查依据任一变化，旧确认失效，创建新候选；不原地更新后沿用 approval。

`receipts/approval.json` 是审计记录，不是仅凭本地文件即可获得权限的令牌。候选 artifact 只含冻结的 `site/ + control/`，外层回执不参与其自引用摘要；部署须从可信准备 run/平台元数据查证运输身份，不能只信调用者提供的 JSON。真正部署仍需当前用户授权和可信工作流的身份、权限检查。部署与线上核对记录在外层追加，不修改冻结前的检查报告。

## 6. 检查矩阵：分别给证据

| 检查 | 对象 | 通过能说明什么 |
| --- | --- | --- |
| 仓库 CI | 固定 `source_sha` | 该源码的已配置自动测试通过；不是发布确认 |
| 精确文件集与禁入规则 | 候选 `site/` | 允许文件、manifest、字节一致，无已知禁入路径 |
| 本地引用闭包 | 候选根本身 | HTML/CSS 链接在候选内存在，不能回退查仓库补缺 |
| 动态资源/封存包 | JS 载荷、资源清单、manifest | 固定资源可用且版本/哈希正确；配合浏览器验证动态分支 |
| 独立学生 ZIP | ZIP 自包含资源与学生载荷 | CRC、路径、引用闭包及教师内容排除符合规则 |
| 构建与验证依据 | 受影响节及共享组件 | 当前证据绑定当前输入与工具，不采用旧截图刷绿 |
| 浏览器与打印 | 候选 HTTP 的代表页/受影响页 | 实际渲染、门禁、锚点、实验、手机与打印对应场景正常 |
| 数学/教学复核 | 本次涉及的内容与模型 | 只覆盖明确复核对象；纯发布组织变化不重审全书 |

复用 `check_release.py --site-root` 做一项引用检查，但要补白名单、JS/资源、ZIP 和证据校验。默认 `check_release.py` 绑定仓库根、含 101 节/101 ZIP 假定、写 `release-checks/static.json`；不能对候选树套用默认 audit 后声称候选已验收。

CI 成功属于自动检查结果。浏览器、数学与教学状态显式记录为 `passed / pending / not-applicable / failed` 并附范围；不设一个模糊的总 `passed` 抹掉待核问题。发布确认必须展示保留的限制及其是否阻断本次发布。

## 7. 确认与部署：不重新构建另一份

目标状态为：

```text
固定源码 -> 已组装 -> 自动检查完成 -> 待确认
    -> 明确确认该候选 -> 部署同一文件树 -> 线上核对
```

任一阻断检查失败，不能进入待确认。确认拒绝则保留问题记录，不反复触发部署。任何冻结依据变化，都回到新候选，而不是修改旧记录。

### 建议分成准备与部署两个入口

1. **准备入口（拟新增）：** 固定 SHA、检查对应 CI、按策略组装、检查、上传含 `site/ + control/` 的候选工件。只有读取代码和上传工件的权限，不给 Pages 部署权限。
2. **确认界面/报告：** 显示 release ID、完整 SHA、候选摘要、增删改、检查范围、未审定项和候选保留期。用户确认的是这个版本，不是泛泛“最新 main”。
3. **部署入口（拟改造）：** 输入可信准备 run/artifact ID、SHA 和候选摘要；核对仓库、工作流、成功状态和身份，下载对应冻结工件，再验文件树与报告。不接收任意 URL 或不可信 PR 上传的工件。
4. **上传 Pages：** 仅上传已校验的 `site/`。可以按 Actions 格式重新封装相同文件树，不能重新渲染、重新读取浮动 main、重新拷贝工作区或补入缺文件。
5. **线上核对：** 保持 Pages 项目子路径、中文路径、iframe、版本资源和旧 URL。核对入口、受影响页及相关资源的字节/功能；分别记录部署 SHA 与核对结果。

GitHub environment 的 required reviewers 是否可用、是否已配置，需实施时查询，**当前不假定已启用**。如果环境审批不可用，要明确人工确认与工作流校验的实际保障和限制；简单的输入框或仓库内 approval 文件不能冒充平台权限门槛。

不使用不受信任的 `workflow_run`/PR 产物进入有写权限的部署流程。并发发布使用唯一通道；对旧候选发布要明确标为回退或指定版本，不让晚完成的旧流程无意覆盖新版本。

## 8. 存储、回退与中断恢复

- 不给每一步全量复制一份网站。每个候选保留一个文件树和小型控制资料；复用 CI 环境与依赖，不增加常驻服务。
- 候选保留期与数量在实施时显式配置。过期后需要重新准备，不能悄悄下载“近似版本”。
- 回退使用上一已确认候选或固定提交重建并重新校验；清楚说明是原工件回退还是新重建。保留旧 URL 与审核依据。
- 新方案未验收前保留旧工作流文件，但接管后不能让旧绕行入口继续无检查部署。切换需要专门验收与授权，不靠删除文件完成迁移。
- 失败保留报告；无授权不自动清理用户试点、原来源或旧版本。清理临时候选须限定任务与保留政策，释放空间用 MB 对账。

本轮完成 **R0：有来源依据的发布设计**。以下 R1–R4 尚未执行，拆开交付，不一次改完所有流水线。

| 工作包 | 限定写入 | 验收与退出条件 |
| --- | --- | --- |
| R1 本地候选组装器 | 发布 policy、独立组装 CLI、其单元测试、临时目录忽略规则 | 先用小型 fixture 验证固定 SHA、白名单、禁入、symlink/越界、额外文件/改字节、dirty 工作区、中文路径和新路径待确认；再只生成一次真实候选，不部署 |
| R2 候选验证与报告 | 候选检查 CLI、现有 checker 的可复用纯函数、测试 | 只检查候选，不改来源/网页；支持动态资源/ZIP/当前依据；缺项失败，不能借仓库补依赖；区分数学/视觉限制 |
| R3 准备/确认工作流 | 独立准备 workflow、候选报告和 artifact 校验 | 无 Pages 权限的准备可以独立运行；拒绝外仓、错误 SHA、过期/篡改工件、待确认新增和无匹配确认；上传回执不回写候选，明确平台审批条件 |
| R4 接管部署 | Pages workflow 与上线核对脚本/文档 | 明确授权后，证明上传的是确认候选；确认后 site/策略/工具/checks 任一改变必须拒绝；阻止旧绕行、验证回退与线上一致后才算接管 |

R1 不依赖正文渲染组件重构，避免把两类风险揉进一个变更。首次真实组装之前先估算单份候选体积，复用现有成品，不重提取、不全书重打 PDF；测试中间树按既定范围清理。
